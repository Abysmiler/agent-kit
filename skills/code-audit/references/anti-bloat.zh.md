# 反膨胀审计要点（Anti-Bloat Audit Focus）

当审计请求提到过度工程、膨胀、去膨胀、不必要的复杂度、不必要的依赖、"我们能删掉什么"、YAGNI，或仓库/模块变得过大时，使用本参考文档。

来源纪律：

- 从仓库自身最大的既有技能及其评审/审计惯例中推导本要点。
- 不要从本技能的小型评审衍生品推导完整审计行为。
- 不要把完整审计变成代码高尔夫。规则是"lazy means efficient, not careless"（偷懒意味着高效，而非草率）。

在简化过程中应用以下阶梯：

1. 它到底需要存在吗？
2. 标准库能做到吗？
3. 平台原生功能是否已覆盖？
4. 已安装的依赖能否解决？
5. 同样的行为能否用一行直白的代码或一个更小的局部代码块表达？
6. 只有在此之后才推荐最小的新代码或新抽象。

在相关时，在 `FULL.md` 发现和中文 `REPORT.md` 中使用这些反膨胀标签：

- `delete`：死代码、未使用的弹性设计、投机性功能、冗余兼容路径、纯转发的包装器，或只导出一个琐碎内容的文件。
- `stdlib`：语言、运行时、框架或数据库已经提供、却被手写实现的功能。
- `native`：依赖或自定义代码做了平台已经提供的事情，例如浏览器控件、CSS、数据库约束或内建格式化。
- `yagni`：单实现接口、单产品工厂、没人设置的配置、单调用方的层，或"以后会用"的脚手架。
- `shrink`：用更少的文件、更少的分支、更少的状态，或更清晰的局部表达实现同样行为。
- `reuse`：存在平行抽象，而本应扩展项目既有的入口点。

按最大安全缩减优先排序反膨胀发现，但安全边界高于行数。绝不建议删除信任边界校验、防数据丢失措施、安全控制、无障碍基础、迁移保障、有意义的测试、明确要求的行为，或真实世界的校准/配置参数。

当一个有意的捷径可接受但有已知上限时，建议记录一个带上限与 revisit 触发条件的受追踪技术债标记，而不是假装它普遍正确。
