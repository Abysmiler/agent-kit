# 系统化调试

停止"猜一个、补一个"式的调试。回到证据,持久化有用的状态,找到根因,做一次最小修复,并验证最初的症状。一次困难的排查解决之后,可以选择把学到的东西沉淀为工程笔记。

## 第一部分:进行中的调试

### 持久化状态

只有在能节省后续工作时,才把调试状态写入 `.agent-work/debug/`:长时间或反复进行的排查,或者很可能超出上下文窗口寿命的排查。

```text
.agent-work/debug/
├── INDEX.md       # 三张表:Active / Unresolved / Resolved,列为 file | summary
├── active/        # 当前排查
├── unresolved/    # 已暂停或仍然失败
└── resolved/      # 已验证的修复
```

在 `INDEX.md` 中,`file` 是笔记的相对路径,`summary` 说明后来的代理为什么应该读它。每个问题一份笔记:

```md
# <一行描述症状>

- Repro: <最小的命令或手工步骤>
- Confirmed observations: <在代码、diff、日志或输出中核实过的事实>
- Failed approaches: <试过什么,为什么是错的>
- Current hypothesis: <根因看起来是 X,因为证据 Y>
- Next diagnostic: <下一个单一检查>
- Resolution: <修复方式与验证命令,验证后填写>
```

只记录已确认的事实,不记录猜测或完整日志。继续处理一个已知问题之前,以及任何一次上下文压缩之后,先重读 `INDEX.md` 和相关的 `active/` 或 `unresolved/` 笔记,再做其他事情。

### 工作流

1. **回到证据。** 说明这是一次系统化排查,下一步是收集证据。检查工作区状态、上一次尝试的修复、失败的命令及其完整输出,以及用户关于"哪里仍然失败"的反馈。子代理报告、先前的总结和你自己的假设,在代码、diff、日志或测试输出中核实之前一律视为不可信。
2. **恢复或创建状态。** 如果 `INDEX.md` 存在就先读它。对长时间或反复进行的排查,创建或更新一份 `active/` 笔记并登记到索引。
3. **复现失败。** 运行能展示该 bug 的最小命令或手工流程。完整阅读错误信息、堆栈、日志或界面症状。如果本地无法复现,指出缺少哪些证据并去收集诊断信息,而不是猜测。
4. **追踪根因。** 检查最近的 diff。沿着错误数据、错误状态或失败的控制流向上游追溯到源头。在多组件路径上逐个检查边界:调用方到被调用方、UI 到状态、API 到服务、服务到持久层、配置到运行时。与同一代码库中类似且正常工作的实现做对比;当框架或外部 API 的行为不确定时,查阅一手文档。
5. **只形成一个假设。** 把它写下来:"根因看起来是 X,因为证据 Y。"用最小的诊断或读代码检查来验证。一次只改一个变量;绝不叠加推测性修复。假设变化时更新笔记。
6. **建立一个会失败的回归验证面。** 优先使用针对此 bug 会失败、且检查真实行为的自动化测试。没有测试框架时,定义最小的可重复脚本或手工复现步骤。
7. **实施最小修复。** 修复已确认的错误行为源头,而不是在症状处加防护。不做无关重构、大范围重写、兼容层或隐藏的回退逻辑。如果直接修复会恶化一个过大的模块、归属不清的状态或测试不足的核心路径,先暂停并说明所需的最小使能重构。
8. **先验证,再声称有进展。** 重新运行最初失败的命令或复现步骤,然后运行相关的测试、类型检查、构建或 UI 验证。报告确切的命令和结果;如果某项检查无法运行,说明阻塞原因。已验证:把笔记移到 `resolved/`。中止或仍然失败:把笔记移到或保留在 `unresolved/`。两种情况都要更新 `INDEX.md`。
9. **反复失败后升级。** 一轮排查失败时,带着新结果回到第 1 步,而不是再叠一层修复。针对同一症状三次修复尝试都不成功后,停下来,与用户一起重新评估架构、状态归属、并发、过时的假设或测试本身的有效性,然后再尝试新的实现。

### 子代理

只委派有边界、可独立验证的调查工作:追踪调用链、对比相似实现、分诊测试输出。假设、修复、diff 审阅和验证由主代理负责。

## 第二部分:沉淀工程笔记

只有在用户提出要求,或者一次已解决的排查产生了明显可复用的知识且用户同意时,才执行本部分。它面向已稳定的证据,不用于仍在发生的 bug。

### 工作流

1. **盘点证据。** 阅读 `INDEX.md` 以及 `resolved/`、`unresolved/`、`active/` 下的相关笔记。如果用户指明的问题没有调试记录,先检查 `git log`、相关提交的 diff 和附近的历史文档,再判断证据是否缺失。先前的总结只当作线索;对照笔记、diff、日志、测试或官方文档加以核实。
2. **给每条发现分类。**
   - `docs/engineering-notes/`:可迁移的知识——官方文档未覆盖的框架或宿主行为、调试方法和决策树、失败特征以及如何区分相似的失败、API 注意事项、验证规程。
   - 其他 `docs/` 文件,例如 `docs/<topic>-implementation-notes.md`:项目专属内容——产品行为,类、函数和参数名称,默认值,本地调试开关和路径,当前的架构与归属选择。
   - 如果一条发现两者都需要,就拆开,并从工程笔记链接到实现笔记。
   - 具体的调试记录留在 `.agent-work/debug/` 作为证据链;不要把整段日志抄进笔记。
3. **按失败模式拆分。** 每个独立的关注点或失败模式一份笔记。不写大杂烩笔记;只在能避免混淆的地方加交叉链接。
4. **从读者的任务出发来写。** 读者正在实现类似的能力,或面对同一类 bug,并且必须能在不读原始代码的情况下跟上推理。优先写分层契约、数据流边界、失败特征、诊断命令和验证面,而不是逐个符号的实现细节。
5. **同时记录成功与失败。** 给出正确的模型或修复模式,以及每一种失败的做法和它为什么是错的。

### 笔记必备结构

`docs/engineering-notes/` 下每个有分量的文件都包含:

- 标题。
- `Last updated: <YYYY-MM-DD HH:MM TZ>`。
- `Reference commit: <完整 git 提交哈希>`。
- `Observed versions: ...`,当行为依赖于宿主应用、操作系统、框架、库、SDK、服务、模型或工具的版本时。
- 官方 API 或文档基线,当涉及外部行为时。
- 带版本的观察记录,用于官方文档未承诺或与官方文档相矛盾的行为。
- 复现推理所需的分层或模块定义:状态归属、数据流、API 或生命周期边界、坐标空间,或该领域的等价物。
- 诊断清单或证据来源。
- 正确的解决方案或修复模式。
- `Previous Wrong Attempts`,作为最后一节:试过什么、为什么失败、如何识别这种失败模式。

### 官方文档

- 对稳定且文档完善的行为,不要重复官方文档。只记录它在所观察版本上遗漏、含糊或表述错误的内容。
- 用一手来源核对外部行为:官方文档、SDK 头文件、源代码、变更日志、issue 跟踪器,或经核实的本地版本输出。
- 明确区分:"官方文档称……"、"在 <版本> 上观察到……"、"官方 API 不保证这一点……"。
- 如果无法从仓库或环境中确定版本,询问用户或标记为未知。绝不把没有版本信息的宿主行为当作普遍事实。

### 验证与报告

- 在 `docs/engineering-notes/` 中搜索项目专属的名称、本地路径、默认值和产品描述;除非它们属于在项目之外也有用的带版本观察,否则移出去。
- 确认每份工程笔记都有时间戳和参考提交,且每一处文档缺口或矛盾都写明了所观察的版本。
- 运行 `git diff --check`。对纯文档改动,说明因此没有运行代码测试。
- 报告:两处位置中创建或更新的笔记、使用的证据来源、验证命令及结果,以及仍然未知的版本或证据缺口。
