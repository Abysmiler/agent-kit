# 章节规划指南

使用本指南将一个大型功能划分为可评审的章节（section），同时不丢失功能级的一致性。

## 1. 围绕行为与不变量规划

一个有用的章节不仅仅是文件的分组。它是系统行为的一个有边界变更，拥有明确的所有者、显式的依赖和一个可测试的完成条件。

从四张图开始：

1. **结果图** —— 用户、运维人员、API 消费者或后台系统的结果。
2. **不变量图** —— 在每个中间状态和最终状态都必须成立的事实。
3. **所有权图** —— 拥有状态、决策与副作用的模块或服务。
4. **依赖图** —— 另一个章节得以推进之前必须存在的契约。

不要一开始就给前端分一个章节、后端分一个章节、测试分一个章节。那会产生横向的部分性工作，其正确性直到集成晚期才能被观察到。

## 2. 优先的章节类型

### 2.1 行走骨架

当架构、部署路径、数据流或集成路径不确定时，使用行走骨架（walking skeleton）。实现最细的端到端路径，以证明主要组件能够通信，并且校验环境能够观察到结果。

行走骨架应当：

- 触发真实的入口与出口点。
- 使用预期的所有权与依赖方向。
- 包含最小的测试或演示路径。
- 避免过早铺开宽度与打磨。
- 产出能够改变后续章节设计的信息。

除非计划明确说明，它不是一次性原型。

### 2.2 垂直行为切片

这是默认选择。一个垂直切片章节只跨实现该结果所必需的层级，实现一个连贯的结果。

示例：

- 端到端注册一种账户类型，包括校验、持久化、API、UI 状态与测试。
- 支持一种新的导出格式，从请求一直到生成工件与下载行为。
- 增加一个受权限控制的操作，包括策略求值、UI 交互元素、审计记录与拒绝测试。

垂直章节可能触及多个模块。可评审性来自单一行为与单一契约，而不仅仅来自较少的文件数。

### 2.3 使能重构

仅当没有接缝、稳定所有者或特征化测试覆盖，后续行为就无法安全地加入时使用。

使能重构必须：

- 保持可观察行为不变。
- 在同一章节之前或之内具备保护性测试。
- 建立指名的后续章节所需的特定边界。
- 避免与功能无关的大范围清理、重命名或抽象。
- 可独立回退。

把大规模的移动/重命名与语义变更分开，使评审者能够区分结构与行为。

### 2.4 展开–迁移–收缩

用于不兼容的 API、schema、事件格式、状态表示或共享接口。

- **展开：** 在保留旧路径的同时，加入向后兼容的新路径。
- **迁移：** 逐步迁移消费方、数据或流量；同时观察两条路径。
- **收缩：** 仅在证据证明迁移完成之后移除旧路径。

每个阶段应有自己的章节或小簇。在开始展开之前先记录收缩阶段的退出条件，否则临时的双路径状态可能变成永久状态。

### 2.5 按抽象分支

在稳定的接缝之后替换大型实现时使用。

典型章节序列：

1. 在不改变行为的前提下引入或验证一个抽象。
2. 让当前实现经由它运行。
3. 在同一契约之后加入新实现。
4. 迁移选定的调用方或流量。
5. 让新实现成为权威。
6. 在合适的时候移除旧实现与临时接缝。

不要只是为了把计划装扮成渐进式而引入抽象。它必须收窄一个真实的语义边界。

### 2.6 功能开关切片

当不完整的行为必须与可部署分支共存，或发布需要受控曝光时，使用发布开关。

每个开关都需要：

- 所有者。
- 默认状态与安全的旧行为。
- 范围或人群语义。
- 相关开/关状态的测试矩阵。
- 发布与回滚方式。
- 过期或移除章节。

不要用开关向测试隐藏破损的中间状态。

## 3. 章节质量测试

一个候选章节只有当所有适用问题都有良好答案时才可接受。

### 连贯性

- 该章节是改变一个相关行为，还是建立一个必要的接缝？
- 它的目的能否不带“以及还要……”式从句地陈述？
- 重构、生成物扰动、格式化与行为是否已解耦？

### 独立性

- 所有前驱是否显式？
- 该章节能否在不猜测未来契约的情况下实现？
- 它能否在不回退无关章节的情况下回退？

### 可测试性

- 是否存在用于判定完成的确定性判定基准（oracle）？
- 能否在未来章节尚未存在时就触发关键路径？
- 负面、边界与失败情形是否已指名？

### 可评审性

- 评审者能否从契约与差异中理解意图？
- 影响锥是否被限制在一次评审会话能够处理的范围内？
- 生成文件、锁文件、迁移或机械性编辑是否已被分离或明确标注？

### 可集成性

- 该章节之后仓库是否仍可构建、可运行？
- 临时的兼容性状态是否显式且安全？
- 该章节的下一个消费方是否已指名？

### 功能连贯性

- 该章节推进了哪些功能级验收标准？
- 它触及哪些全局不变量？
- 哪些内容被有意延后？

## 4. 规模启发式

不要把行数当作唯一的切分依据。把它与语义广度一起作为警告信号。

一个常规章节通常应满足以下启发式：

- 一个主要行为或接缝。
- 一次实现者会话与一次评审者会话。
- 少数几个语义所有者。
- 在可行时大致 100–400 行行为代码，不包括生成文件、快照、锁文件与纯移动。
- 除非各边界不可分割，不超过一个高风险语义边界。

在以下情况下再次拆分：

- 该章节需要多个独立的验收判定基准。
- 其契约包含多个互不相关的结果。
- 它同时改变一个提供方契约和许多消费方，却没有兼容性阶段。
- 它混合了数据迁移、运行时切换与旧路径移除。
- 评审需要反复在互不相关的工作流之间切换。
- 实现无法停留在一个有效的中间状态。
- 修复影响锥几乎等于整个功能。

也不要拆得过细，使新的 API 或抽象没有真实用途。一个章节必须仍然可以理解为一个可工作的增量。

## 5. 依赖图

在 `PLAN-FULL.md` 中显式表示依赖。

使用以下边类型：

- `requires`：前驱被接受之前无法开始实现。
- `integrates-with`：各章节可独立构建，但需要一起做一次检查点。
- `migrates-from`：消费方或数据迁移依赖于已展开的兼容路径。
- `contracts`：在所有迁移被证明完成之后，清理移除临时路径。
- `conflicts-with`：章节不能并行，因为它们修改同一个语义所有者。

该图必须无环。若两个章节互相依赖，说明边界错了，或者缺少一个行走骨架/公共契约章节。

## 6. 需求覆盖矩阵

把每条完整功能标准映射到实现与验证。

```markdown
| Requirement | Primary section(s) | Section oracle | Integration oracle | Status |
|---|---|---|---|---|
| R-01 | S01, S03 | targeted test | end-to-end flow | planned |
| R-02 | S02 | schema test | migration rehearsal | planned |
```

任何需求不得只靠“最终测试”覆盖。那通常意味着章节设计没有局部判定基准。

还要映射非功能性需求：

- 安全与授权。
- 隐私与数据保留。
- 并发与顺序。
- 可靠性、重试与幂等。
- 性能与成本上限。
- 可观测性与运维控制。
- 无障碍与 UX 状态。
- 迁移、发布、回滚与恢复。

## 7. 规划跨章节契约

对每个生产者-消费者关系，记录：

- 权威所有者。
- 数据或控制契约。
- 版本或兼容状态。
- 错误与回退语义。
- 顺序与幂等假设。
- 传递的安全/权限上下文。
- 在生产者一侧证明该契约的测试。
- 在消费者一侧证明该契约的测试。
- 证明组合路径的集成检查点。

当存在运行时序列化、持久化、权限或部署边界时，不要依赖“两个章节使用同一类型”作为证明。

## 8. 并行化决策

并行工作是优化，不是默认。

一对章节只有在以下条件全部成立时才可并行：

- 任一章节都不依赖另一章节的代码或已接受行为。
- 它们不修改同一个状态所有者、schema、公共契约、迁移或中央协调者。
- 它们的测试夹具与生成工件不冲突。
- 它们的分支/worktree 相互隔离。
- 集成顺序与检查点已预先确定。
- 冲突可以在不发明新语义的情况下解决。

不确定时，顺序执行。并行代理可以提升吞吐量，但也会成倍增加集成状态与评审者负担。

## 9. 硬上限再分解

当一个活跃章节经过三轮计数评审仍未获得一次干净的轮次时，不要自主增加评审预算。把这些轮次报告当作经验证据：该章节边界对代理式的实现/评审而言可能是错误的。保留失败尝试，并停在硬上限用户决策处（`continue` / `split` / `accept-risk` / `block`）。

只有记录在案的 `split` 选择才会调用 `[tier: plan]` 分解者。它应只拆分失败的章节，并保留已接受的前驱以及原始功能契约。使用层级式 ID，例如 `S03.1`、`S03.2`；若 `S03.1` 随后失败，再次呈现决策，若再次选择 `split`，使用 `S03.1.1`、`S03.1.2`。

把谱系 ID 中的点数计为递归拆分深度：`S03` 为深度 `0`，`S03.1` 深度 `1`，`S03.1.1` 深度 `2`，`S03.1.1.1` 深度 `3`。在每个硬上限决策中报告该深度；在深度 `3` 时，建议对功能边界重新规划，而不是深度 `4+` 的拆分。

好的拆分轴包括：

- 每个后代一个可观察行为；
- 在可行时每个后代一个权威的状态/所有权边界；
- 契约引入与消费方迁移分离；
- schema 展开、数据迁移与收缩/移除分离；
- 使能重构与行为分离；
- 策略定义与执行集成分离；
- 生产者与 worker/重试/死信行为分离；
- 被不同评审轮次反复暴露的根因类别拆分为独立判定基准。

一次有效的再分解必须更新：

- 需求覆盖矩阵；
- 依赖图与下游 `Requires`；
- 集成检查点；
- 延后工作归属；
- 章节谱系与重规划代数。

不要仅仅因为代码已经存在就保留失败的实现结构。重试从失败父章节的原始 `section_base` 开始；备份分支用于取证对比与恢复，而不是作为新的实现基点。

## 10. 常见反模式

### 横向分层计划

```text
S01 database
S02 backend
S03 frontend
S04 tests
```

问题：没有任何章节拥有可观察的结果，测试在设计错误已经叠加之后才到来，最后一个章节成了第一次真正的集成。

改进：按结果切片，只在必要处设置契约或迁移章节。

### 每个目录或文件类型一个章节

问题：文件布局不是语义边界。评审者仍然需要整个功能才能判断某个章节是否正确。

### 带投机性抽象的“地基”章节

问题：代理在没有实际使用证据的情况下设计 API，后续章节继承了错误假设。

改进：让新接缝至少伴随一个真实用途或行走骨架。

### 最后的“把一切接起来”章节

问题：所有跨章节风险都被推迟到最大、最难评审的步骤。

改进：在每个依赖簇之后定义集成检查点。

### 重构与行为混合

问题：移动与语义互相遮蔽，使缺陷更难发现、回退更难执行。

改进：先做带特征化测试的使能重构，再做行为。

### 并行的相互依赖代理

问题：两个代理各自发明共享契约，导致不兼容的实现或一个巨大的调和补丁。

改进：在一个已被接受的前驱章节中冻结共享契约。

### 以改动的文件定义“完成”

问题：代理为产出量而优化，而不是为行为。

改进：定义可观察的验收标准与命令。

## 11. 示例分解

功能：增加带每租户配额的可续传批量上传。

```text
S00  Walking skeleton: one small upload travels through UI, API, storage, and status readback.
S01  Quota policy owner and denial behavior with unit/contract tests.
S02  Expand upload session schema/API for resumable offsets; old single-shot path remains valid.
S03  Implement server-side chunk validation, idempotency, and recovery.
S04  Implement client resume flow and user-visible states behind a release flag.
CP1  Integrate S01–S04: quota + interrupted upload + resume end to end.
S05  Migrate eligible callers and telemetry dashboards.
S06  Rollout controls, cleanup, documentation, and remove obsolete path after evidence.
FINAL Cross-section acceptance, migration rehearsal, rollback, security, performance, and flag-lifecycle review.
```

该计划拥有垂直结果、显式的高风险边界、中途的集成检查点，以及明确的收缩阶段。
