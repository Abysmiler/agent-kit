# 集成与收敛指南

使用本指南区分章节接受与功能就绪，并解释“单次干净评审接受 / 三轮硬上限”策略。

## 1. 评审角色

### SECTION

第 1 轮对一个已冻结章节范围及其直接影响锥做完整评审，使用全新的评审者上下文。之后的计数轮次是 `DELTA` 评审（见下）。

可能的局部结果：

- 重大可执行问题；
- 没有新的重大可执行问题；
- 被真正的决策/证据缺口阻塞。

某个计数轮次是否干净，由父工作流决定，而不是由个别评审者决定。

### DELTA 计数轮次

修复之后，计数轮次是针对修复增量及其失效影响锥的 `DELTA` 评审。`delta-verified`（增量验证通过：全部冻结问题已关闭、影响锥内无新的阻塞性缺陷）即为干净的计数轮次，并接受该章节。只有重置触发器生效后才再次运行完整 `SECTION` 评审，因此稳定范围绝不被重扫。

### INTEGRATION

在已接受的活跃叶子章节于实际功能 head 上组合完成之后，对组装后的功能做跨章节评审。它聚焦于涌现行为，而不是重放每一条章节代码。

## 2. 单次干净评审的章节接受

只有当以下条件全部成立时，章节才被暂时接受：

- 章节契约与 base/head 稳定且已记录；
- 必需的检查通过，或外部证据阻塞项已被明确说明；
- 没有未解决的 `Must Fix`（必须修复）、未接受的 `Should Fix`（应当修复）或阻塞性 `Needs Decision`（需要决策）；
- 延后的工作有明确的后续所有者，且不会使当前中间状态无效；
- 一个计数轮次是干净的：第 1 轮覆盖完整的完整 `SECTION` 评审未发现新的重大可执行根因，或修复后 `delta-verified` 的轮次。

计数评审者绝不能被预先告知“上一轮是干净的”、先前的诱导性结论或修复叙述。共享冻结的问题 ID 与已关闭根因 ID（仅 ID 与一行标题）以防重新提出已关闭的问题。

## 3. 三轮硬上限

对每个活跃章节尝试：

- 计数轮次最多：**3** 次（第 1 轮完整、修复后 `DELTA`）。
- 软上限：**无**。
- 接受条件：在这三轮之内出现一次干净的计数轮次。
- 没有明确记录在案的用户 `continue` 决策，同一章节尝试禁止第 4 轮。

示例：

```text
R1 clean
=> accepted in 1 round
```

```text
R1 findings -> repair
R2 delta-verified
=> accepted in 2 rounds
```

```text
R1 findings -> repair
R2 delta findings -> repair
R3 delta findings -> repair
=> not accepted; hard-cap user decision
```

## 4. 硬上限用户决策

三轮未收敛的计数评审被视为关于分解的证据——但回应方式是用户决策，而不是自主重写。常见的证据模式：

- 多个相互独立的行为被放进了一个章节；
- 一个章节跨越多个状态/所有权边界；
- 修复反复扰动相邻契约；
- 测试判定基准过宽或过于间接；
- 展开/迁移/收缩各阶段被压缩在一起；
- 使能重构与功能行为纠缠；
- 隐藏的跨章节依赖被留在了章节内部。

因此决策过程会：

1. 把失败的代码状态保留在 `agent-kit/backup/***` 上；
2. 连同根因模式一起总结全部计数轮次；
3. 请用户按顺序选择：`continue`（最多两个额外计数轮次）、`split`、`accept-risk` 或 `block`；
4. 选择 `split` 时，让一个 `[tier: plan]` 子代理只对该章节再分解，校验新的后代计划，并从失败父章节的原始 `section_base` 重新开始实现——只有决策明确授权时才可保留（salvage）失败尝试的提交；
5. 选择 `accept-risk` 时，把每条剩余问题记录为显式债务/决策，并将该章节标记为带债务接受。

绝不在硬上限处自主丢弃接近收敛的工作或开始重新实现；该权衡由用户拥有。

## 5. 集成检查点

当后续章节开始使用新建立的跨章节契约时使用检查点（integration checkpoint），包括：

- API 生产者 + 第一个真实消费者；
- schema 展开 + 读/写迁移；
- 权限策略 + 执行路径；
- 生产者 + 队列/worker + 重试行为；
- 新的状态所有者 + 下游消费者；
- 功能开关 + 新旧路径对等性；
- 组合之后的独立开发分支。

检查点证据应包括组合 head、所含章节、被测契约、正常/负面/部分失败路径、命令/结果、回滚/停用路径，以及已知的尚未包含的章节。

检查点结果：

- `checkpoint-passed`；
- `checkpoint-blocked`；
- `checkpoint-insufficient-evidence`。

当实际组合推翻了某个章节假设时，检查点可以使先前的局部证据失效。保留原始的评审/重规划谱系，而不是改写历史。

## 6. 最终集成评审

当所有活跃叶子章节被接受之后，收尾该功能。仅当至少一条成立时才运行最终 `INTEGRATION` 评审：功能跨越了高风险语义边界；被接受的活跃叶子章节超过三个；发生过硬上限拆分；或用户/governing instructions 明确要求。否则以确定性的完整功能校验套件加上最后一个章节的评审证据收尾。

当评审运行时，对照原始契约评估组装后的功能，不重放已接受的局部代码。

### 原始意图

- 行为是否满足原始的用户/运维结果？
- 非目标是否仍被遵守？
- 每条需求是否都映射到了实现与证据？

### 跨章节契约

- API 请求/响应与错误语义；
- schema/数据所有权与迁移顺序；
- 状态所有权与同步；
- 授权/租户一致性；
- 事件顺序、重试、幂等、取消；
- 共享 UI 状态与加载/错误/空状态；
- 清理与功能开关生命周期。

### 端到端与运维

- 有代表性的正常路径；
- 负面权限/输入路径；
- 部分失败/重试路径；
- 回滚/停用行为；
- 日志/指标/追踪/审计信号；
- 相关场景下的性能/资源边界；
- 安全/隐私/机密处理；
- 文档/配置/运行手册完整性。

### 分支完整性

- 只存在与功能相关的变更；
- 生成工件可复现；
- 测试没有被削弱以强行变绿；
- 临时脚手架已被移除或被明确归属；
- 活跃后代 head 与评审证据对应实际的功能 head。

## 7. 重置与证据失效

当一次重大变更改变了以下内容时，该章节评审尝试应被视为新的基线：

- 章节目标或验收标准；
- 公共 API/序列化契约；
- schema/数据所有权/迁移顺序；
- 认证/授权/租户/隐私语义；
- 并发/顺序/重试/幂等/破坏性行为；
- 架构/状态所有者/依赖方向；
- 发布/回滚/功能开关语义；
- 超出已冻结契约的范围；
- base/head 超出被跟踪的实现/修复操作。

硬上限再分解强于普通重置：父尝试被退役，后代从父章节的原始基点开始。

## 8. 人类决策点

需要用户/负有责任的所有者：

- 含糊的业务/产品行为；
- 兼容性策略选择；
- 迁移/回填含义；
- 可接受的数据/安全/运维风险；
- 尚未指明时的发布人群/时机策略；
- 相互冲突的权威需求；
- 三轮评审硬上限（continue / split / accept-risk / block）。

在记录 `split` 选择之后，不得仅为以下事项再次要求用户批准：

- 创建硬上限备份分支；
- 调用 `[tier: plan]` 分解者；
- 创建重试分支/worktree；
- 提取第一个后代并恢复实现。

这些跟随已记录的决策，在已委托的执行权限下进行。在谱系深度 `3` 时，进一步拆分应建议对功能边界重新规划，而不是深度 `4+` 递归。

## 9. 最终就绪门禁

只有在以下条件全部成立时才判定 `mergeable`（可合并）：

- 所有活跃叶子章节均被暂时接受；
- 因硬上限拆分而退役的父章节拥有完整的谱系/证据；
- 所有完整功能需求均已覆盖；
- 必需的集成检查点通过；
- 必需的最终门禁——触发条件成立时的 `INTEGRATION` 评审，否则为确定性完整功能校验套件加上最后一个章节的评审证据——没有未解决的重大合并阻塞项；
- 完整功能确定性检查通过，或明确的外部阻塞项/残余风险已被报告；
- 发布、回滚、迁移、可观测性与清理义务已解决或被明确接受。

否则使用 `not-mergeable`（不可合并）或 `insufficient-evidence`（证据不足）。
