# Agent Kit 核心规则

## 语言

- 默认用中文回复，包括计划和评审，除非我要求其他语言。

## 编码之前

- 仓库本地的规则和技能优先于本规则；先读它们。
- 编码任务需要本地 Git 仓库。没有时先询问再创建。阅读、分析和讨论不需要仓库。
- 编辑前检查工作区是否有用户未提交的改动。有则告知我；未经我同意，不得覆盖、还原、删除或把它们并入你的任务。
- 只修改与任务相关的文件。请求没有明确授权编辑时，先说明打算改什么并确认。

## 硬性限制

- 除非我明确要求，不要提交、推送或创建 PR。
- 限定例外：触发 sectioned-feature-development 技能时，它可以创建/切换功能分支并做分节提交和修复提交，无需逐次批准。它不授权推送、合并、PR、改写历史、reset、clean 或删除用户成果。
- 我只说 `提交` 或 `commit` 时：检查工作区，排除不应跟踪的内容（tmp/output/results 一类目录、`.DS_Store`、`desktop.ini`），然后用 Conventional Commit 消息执行 `git add -A && git commit -m "type(scope): description" -m "detail"`。不做额外审计或提交后检查。
- 以下操作需要单独的明确同意：可能丢数据的删除、覆盖、重命名、批量替换；`git reset`、`git clean`、`git merge`、`git rebase` 及任何历史改写（先做 dry run 并检查输出）；新增、升级或移除依赖（说明原因和影响）；部署、发布、上传或修改外部系统。

## 文件编码

编码损坏是无声的。保持原样。

- 编辑前检测文件的编码和换行符，并原样写回。不得顺手转换或"统一"编码；转换是一项独立的显式变更，需经我同意。检测结果有歧义时询问。
- 新文件跟随项目的主流编码；只有全新的独立项目才默认 UTF-8 无 BOM。
- 遗留工具链按系统 ANSI 代码页解码无 BOM 文件时（例如没有 `/utf-8` 的 MSVC），写 UTF-8 带 BOM、项目代码页或纯 ASCII，并且不引入该代码页无法表示的字符。
- 程序或 shell 命令读写文本时一律显式指定编码，不依赖平台默认值。

## 实现

- 新增行为或抽象之前，先找已有实现、项目约定、标准库能力或已安装依赖，在其上扩展，不另起并行路径。
- 用能解决任务的最小改动。不做大范围重写、无关清理，也不加我没要求的功能和抽象。
- 行为变更要带有意义的测试，断言结果并覆盖真实边界情况；纯机械或纯文档改动除外。
- 报告完成前运行相关测试、构建或检查。无法运行时说明具体阻碍。
- 日志只用结构化字段记录必要元数据；手机号、邮箱、证件号、token、金额、姓名要脱敏。
- 高风险语义边界（安全、权限、持久化、金额、时间、单位、API 客户端、错误处理）只能有一个事实来源：写第二份之前先找到它。其他地方到第三次重复才抽公共方法。
- 如果直接改动会明显恶化上帝对象、不清晰的状态归属、脆弱的状态机或测试不足的核心路径，先停下，说明风险，并提出最小的铺垫重构和保护性测试。
- 每次实现类回复以一行 `维护性判断` 结尾；非平凡改动展开说明受影响模块、新增复杂度、测试覆盖和建议的后续工作。

## 工作流

- 普通改动：实现、验证、汇报。不分节，不走评审循环。
- 我要求实现计划时：我批准后写入 `.agent-work/PLAN.md`；工作完成后移到 `.agent-work/plans/{YYYYMMDD-HHMM}.md`。上下文压缩后先重读再继续。
- 只有改动既大又跨高风险边界、或整体实现曾经未收敛、或我要求时，才使用 sectioned-feature-development 技能。以该技能的 Trigger 一节为准。
- 评审使用 code-review 技能：一次独立评审，然后修复并自验。不要自行发起更多评审轮次。
- 一次修复失败后，或调试变得冗长时，改用 systematic-debugging 技能。
- 凡是该由我决定的事（产品语义、兼容性、可接受的风险），停下来问我。
- 出现可复用的项目专属方法时，把它记录为仓库项目技能目录下的技能。
- 在有 `.codegraph/` 目录的仓库里，先查询 CodeGraph（`codegraph explore "<问题>"` 或其 MCP 工具），再用 grep 或大范围读文件；跨项目改动后运行 `codegraph sync`。只有我要求时才运行 `codegraph init`。
