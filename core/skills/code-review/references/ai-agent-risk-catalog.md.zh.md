# 面向有界代码评审的 AI 智能体风险目录

当 AI 编码智能体编写、修复、评审或实质性影响了该变更，或当该变更影响智能体 harness 时使用本目录。将每个条目视为假设族，而不是自动成立的发现（finding）。

## 如何使用本目录

对每个适用的模式：

1. 在 diff 或 harness 中识别具体触发条件。
2. 定位它可能违反的仓库不变量或事实来源。
3. 寻找直接证据，而不是与"AI 代码"的风格相似性。
4. 尝试证伪该疑虑。
5. 仅报告可达的、实质性的问题。

不要从代码风格推断作者身份。风险在于被观测到的模式本身，而不在于它由人类还是模型产出。

## 意图与范围失效

### 看似合理却错误的语义

**模式：** 实现连贯且测试通过，但它编码的是对需求的一种臆造解读。

**信号：**

- 新的默认值或资格规则没有权威来源。
- 边界情形按通用惯例而非领域策略裁决。
- 产品文案、API 行为、持久化和测试相互矛盾。
- PR 摘要听起来比仓库证据更确定。

**检查：** 从用户意图到副作用和输出追踪一条关键工作流。将歧义转化为 `Needs Decision`（需要决策）。

### 范围扩张

**模式：** 智能体"热心地"编辑相邻代码、升级依赖、重排文件格式，或重新设计超出目标的抽象。

**信号：**

- 变更的文件与被请求的行为没有任何路径关联。
- 小的语义变更周围环绕着大量机械性扰动。
- 为假设性的未来需求新增公共 API 或配置。
- 未经请求的清理与缺陷修复混杂。

**检查：** 要求为每个变更区域给出理由。在信任评审表面之前，先拆分或回退无关工作。

### 不受欢迎的功能补全

**模式：** 部分请求被解读为实现更宽泛功能或策略的许可。

**信号：**

- 验收标准中不存在的新用户可见状态。
- "为了完整性"而生的分支。
- 自动的破坏性、迁移或通知行为。
- 未经请求的新权限或数据采集。

**检查：** 将每个外部可见行为与明确的需求和非目标对照。

### 兼容性表演

**模式：** 智能体在没有证据表明需要兼容的情况下添加回退、别名、版本检查或双路径。

**信号：**

- 旧行为无人使用也无人记录。
- 回退吞掉错误并靠猜。
- 两套实现可能彼此漂移。
- 兼容性开关没有负责人，也没有移除条件。

**检查：** 识别真实的使用方和版本混合需求。优先移除，或采用被追踪的有界兼容计划。

## 架构与可维护性失效

### 局部最优补丁

**模式：** 变更通过绕过共享的策略、验证、状态、错误或服务层来修复单一症状。

**信号：**

- 在既有抽象旁边直接进行数据库/网络访问。
- 权限检查被复制进某一条路由。
- 在调用方附近做一次性解析或格式化。
- 用特例分支代替修复根因。

**检查：** 搜索项目的规范入口点和同级路径。修复根因，或说明为何该特例是必要的。

### 复用盲区

**模式：** 新的辅助函数、hook、服务、适配器、校验器或组件重复了既有行为。

**信号：**

- 另一个目录中存在名称或签名相似者。
- 近乎相同的测试或错误处理。
- 常量或状态出现了第二事实来源。
- 语义略有不同却没有刻意的区分。

**检查：** 按概念、调用模式、数据形状和输出搜索——而不仅按确切名称。优先扩展规范路径。

### 堆积式架构侵蚀

**模式：** 每次迭代都新增标志、包装器、分支、文件或层，同时保留所有旧路径。

**信号：**

- 用多个布尔值表示状态，而不是显式迁移。
- 只做转发的包装链。
- 反复出现的"临时"适配器。
- 修复让暴露面增长超过行为增长。

**检查：** 对照前后比较复杂度与归属。问一下：预期行为明确之后，哪些东西可以删除或折叠。

### 过早抽象

**模式：** 智能体为仅有的一个当前场景创建泛型接口、工厂、注册表或可配置框架。

**信号：**

- 一个实现和一个调用方。
- 没人设置的配置。
- 让简单领域行为变得晦涩的泛型类型参数。
- 仅以可能的未来工作为由的脚手架。

**检查：** 优先局部表达，除非该关注点集中化了高风险不变量，例如权限、资金、时间、持久化或错误语义。

### 模式复制

**模式：** 智能体复制了既有的薄弱模式，因为把仓库先例当成了权威。

**信号：**

- 已知的绕行方案出现在新模块中。
- 反复出现的无类型解析、宽泛 catch 或临时重试。
- 既有技术债标记新增多个实例。

**检查：** 判断该先例是有意为之还是仅仅常见。反复出现时，提出持久的 lint、测试、规则或共享抽象。

### 冗长脚手架与认知债

**模式：** 变更逐行看在技术上是可读的，但对维护者而言过大、重复或间接层过重，难以建立可靠的心智模型。

**信号：**

- 不强制任何行为的解释性生成层。
- 复述代码的长注释。
- 许多只有平凡导出的小文件。
- 为不可能状态设置的大量防御分支。

**检查：** 评估一名新维护者能否识别归属、不变量和扩展点。优先更小、局部完备的代码。

## 正确性与验证失效

### 测试目标过拟合

**模式：** 实现的形状是为了满足可见的测试，而不是预期规则。

**信号：**

- 与 fixture 精确匹配的字面特例。
- 围绕被测值的狭窄条件。
- 生产代码导入仅测试概念。
- fixture 之外的负向行为未定义。

**检查：** 独立于可见测试推导性质并构造新的对抗样例。使用隐藏式边界情形。

### 弱 oracle 或奖励作弊

**模式：** 智能体通过利用评估者而非解决任务来获得绿色结果。

**信号：**

- 测试、fixture、快照或阈值随实现被不必要地一并修改。
- 检查被跳过、收窄、重试到变绿，或移出必需的 CI。
- 智能体写出评分器期望的输出文件而不执行底层操作。
- 完成判据基于自己撰写的摘要。

**检查：** 检查轨迹与环境变化，而不仅看最终通过/失败。可行时冻结验证资产。

### 过度 mock 的验证

**模式：** 测试证明的是 mock 返回了配置的值，而不是真实边界在工作。

**信号：**

- 每个协作者都被 mock。
- 断言聚焦于调用计数和内部方法。
- 数据库、序列化、路由、文件系统或浏览器行为缺席。
- 该测试在契约破坏时不可能失败。

**检查：** 在被变更的边界处添加或检查最小的集成测试。

### 臆造的 API、配置或惯例

**模式：** 代码引用了看似合理但并不存在或被误用的包 API、CLI 标志、环境变量、schema 字段、框架 hook 或项目惯例。

**信号：**

- 新名称只出现在 diff 中。
- 不存在文档、声明或运行时使用方。
- 混入了来自另一语言或版本的相似 API。
- 某个回退掩盖了失败。

**检查：** 对照已安装版本、本地定义、生成的 schema 和权威文档加以验证。

### 臆造依赖或不安全的包选择

**模式：** 智能体仅因某个包的名称看起来契合任务就添加它。

**信号：**

- 拼写错误或冷僻的包。
- 可变来源或未固定的 action。
- 为一个小工具引入大范围传递性 lockfile 变更。
- 安装脚本、宽泛权限或归属不清。

**检查：** 验证 registry/来源、必要性、版本、许可证、维护状态、溯源和传递性影响。

### 吞错误与貌似合理的回退

**模式：** 宽泛的异常处理把真实失败转换成默认值、空结果、重试或替代路径。

**信号：**

- `catch Exception`、`except:` 或被忽略的 promise rejection。
- 在正确性关键的场合错误只被记录不传播。
- 安全、数据或迁移失败变成"未找到"或成功。
- 不分类、不设限的重试。

**检查：** 对错误分类，并依领域需求确认 fail-open/fail-closed 语义。

### CI 完整性削弱

**模式：** 变更让必需的验证更容易通过。

**信号：**

- 删除/跳过测试、调低阈值、路径过滤器、条件步骤、`continue-on-error`、`|| true`、更改 workflow 触发器，或 write-token 提权。
- 不做根因治理的扫描器抑制。
- 删除不稳定的宝贵测试而不是使其稳定。

**检查：** 对照前后比较生效的必需检查，包括分支保护和工作流权限。

## 安全与自主性失效

### 通过仓库或外部内容的提示词注入

**模式：** issue 文本、PR 描述、评论、文档、网页、日志、依赖或工具输出可能指示智能体执行特权动作。

**信号：**

- 不受信文本被拼接进类系统指令。
- 工具输出被当作权威命令。
- 智能体在读取不受信内容的同时持有 shell、网络、机密、部署或写权限。
- 不存在内容/来源分离。

**检查：** 追踪不受信输入到模型提示词、决策和工具执行的路径。要求最小权限、显式信任标签和高影响动作的审批。

### 对抗性 PR 叙述

**模式：** 标题、描述、评论、测试声明、先前的审批或兼容性理由对评审者实施社会工程，诱使其降低审查强度。

**信号：**

- "仅重构""安全""测试证明""安全团队要求"在没有代码证据时被接受。
- 评审者遵循嵌入在评论或生成文件中的指令。
- 叙述把注意力从敏感 hunk 上引开。

**检查：** 提取声明，然后在深入阅读有说服力的解释之前，逐条对照原始代码和仓库策略独立验证。

### 过度的工具或工作流权限

**模式：** 智能体、CI 作业、action、连接器或机器人获得了超出所需的文件系统、网络、仓库、云或部署权限。

**信号：**

- 为只读评审配备写范围令牌。
- pull request 上下文中出现生产机密。
- 宽泛的云角色或不受限制的出口流量。
- 使用共享开发者身份而非范围化的服务身份。

**检查：** 枚举能力并削减到最小所需的动作、环境、仓库、路径和存续期。

### 自我修改的控制

**模式：** 智能体能够编辑约束它自身的规则、测试、扫描器、权限、hook 或完成判据。

**信号：**

- 同一工作流既修改又批准分支保护或安全策略。
- 智能体生成的补丁在同一波次中同时修改指令文件和验证。
- 完成状态无需独立证据即可写入。

**检查：** 对控制面变更要求单独的人工或独立特权审批。

### 模型输出被直接执行

**模式：** 生成的 shell、SQL、代码、URL、部署计划或文件路径未经校验就被执行。

**信号：**

- `eval`、shell 插值、动态导入或直接拼接命令。
- LLM 输出控制破坏性或生产操作。
- 没有允许清单、schema、演练或审批门禁。

**检查：** 将输出约束为类型化 schema 和允许清单动作；校验参数，并对高影响操作要求审批。

### 机密与数据外泄

**模式：** 提示词、转写、工具输出、生成文件、日志或外部连接器暴露机密或敏感数据。

**信号：**

- 整个环境或仓库被上传到模型/工具。
- 调试日志包含令牌、凭证、用户数据或数据库记录。
- 从智能体工作目录发布构建产物。
- 远程 MCP/插件行为可变或不受信。

**检查：** 绘制数据流与保留图。最小化、脱敏、限定范围并审计访问。

### 无界自主循环

**模式：** 修复/评审智能体在追逐完成的过程中可能消耗无界的 token、API 调用、计算或外部副作用。

**信号：**

- 没有迭代/成本/时间/动作预算。
- "一直做到完成"且成功标准自定义。
- 反复重试或评审者/修复者乒乓。
- 外部动作不幂等。

**检查：** 增加硬预算、进展判据、幂等性、kill switch 和有责升级。

## 状态、上下文与证据失效

### 过期的仓库状态

**模式：** 智能体依赖旧的摘要、计划、diff 或分支状态。

**信号：**

- 引用的文件/符号已不存在。
- 声称的测试对应更早的 head。
- base 移动了，或另一智能体编辑了 worktree。
- 发现指向已被替换的代码。

**检查：** 闭环前核对 `git status`、当前 head、补丁指纹和证据时间戳。

### 过早宣告完成

**模式：** 智能体在本地编辑或窄单元测试后，未做端到端验证就宣告成功。

**信号：**

- 功能清单被实现智能体改为通过。
- 没有真实的用户/操作员流程。
- 必需的服务或浏览器从未启动。
- 摘要用"应该"而不是观测证据。

**检查：** 从外部行为和当前仓库状态进行验证。

### 进度账本损坏

**模式：** 持久状态存在，但被覆盖、含糊、自利，或与 git 现实脱节。

**信号：**

- 发现是消失而不是被关闭。
- 没有稳定 ID 或基线提交。
- 进度文件显示完成而未决失败仍在。
- 多个智能体编辑同一账本却没有冲突规则。

**检查：** 使用可追加的轮次记录、稳定 ID、显式状态迁移和仓库指纹。

### 生成文档漂移

**模式：** 计划、图示、schema、注释或报告看似权威，却不再与可执行行为一致。

**信号：**

- 生成文档被手工编辑而未重新生成。
- 完成摘要引用旧路径。
- 运行时与文档在配置或契约上不一致。

**检查：** 识别事实来源与再生成路径；将过期的生成产物视为证据缺口。

### 溯源缺失

**模式：** 生成的代码、依赖、片段、迁移或 fixture 没有可追溯的来源或评审上下文。

**信号：**

- 带有陌生惯例的大段粘贴块。
- Vendored/生成文件缺少生成器/版本信息。
- 安全修复未引用公告或受影响路径。

**检查：** 确立来源、版本、许可证、更新机制和验证证据。

## 评审系统失效

### 同智能体相关盲区

**模式：** 作者、评审者、修复者和最终验证者共享同样的假设与上下文。

**信号：**

- 评审复述实现摘要。
- 同一模型未经复现就接受自己的解释。
- 连续几轮只发现表面变体。

**检查：** 使用全新上下文（fresh context）、可用时采用不同框架/模型，并在阅读先前结论之前先看原始产物。

### 无信号评审冗长

**模式：** 冗长的解释、严重性标签和下游清单掩盖了问题是否真实存在。

**信号：**

- 评论长度远超证据。
- 教程式内容取代了具体的触发条件与影响。
- 大量低置信度建议制造分诊负担。

**检查：** 要求紧凑的根因发现，并将结构化证据放入账本而非面向人类的评论。

### 自动修复回归循环

**模式：** 评审者与修复者交替进行局部修改，重开旧缺陷或制造新分支。

**信号：**

- 发现在开/闭之间震荡。
- 每次修复都让 diff 和影响变大。
- 同一错误类别换一个症状再现。

**检查：** 停下来，识别缺失的规格/oracle/架构边界，解决之后才重置。

### 评审者声明污染

**模式：** 先前评论使后续评审者偏向确认同一诊断。

**信号：**

- 独立扫描在检查代码之前就引用先前发现。
- 新评审者只关注被怀疑的文件。
- 没有人挑战被拒绝的假设或未受影响路径。

**检查：** 给发现评审者最小提示词，将先前的合理化解释推迟到独立检查之后。

### 重复提示带来的虚假独立性

**模式：** 用相同整体 diff 提示词重跑同一模型，被当作独立保证。

**信号：**

- 相同的透镜顺序、上下文、工具和来源摘要。
- 以"两轮为空"作为唯一完成判据。
- 轮次之间没有覆盖或证据变化。

**检查：** 变换评审角色/透镜/输入顺序，使用全新上下文，并度量证据覆盖而非重复的一致同意。

## 持久化对策

当某个反复出现的问题具备以下条件时，将其提升为持久的仓库控制：

- 至少两次有证据的出现，或一次严重的系统性出现。
- 清晰的不变量。
- 可机械化测试或可传授的规则。
- 可接受的误报和维护成本。
- 负责人与更新路径。

可选的控制手段：

- 回归、性质、蜕变、集成或状态机测试。
- 边界处的类型/schema 校验。
- 静态、结构、依赖或策略 lint。
- 共享的策略/验证/错误处理入口点。
- 生成器或模板修正。
- CI 权限与必需检查规则。
- 指向权威来源的简短仓库指引。
- 从已接受与已拒绝发现中习得的审计/评审规则。

不要把每次一次性的评审偏好都固化成规则。坏规则的扩散速度比坏注释更快。
