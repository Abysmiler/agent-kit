# 集成与收敛指南

使用本指南区分章节接受与功能就绪，并解释“单次干净评审接受 / 五轮硬上限”策略。

## 1. 评审角色

### SECTION

对一个已冻结章节范围及其直接影响锥的完整评审。每个计数轮次都使用全新的评审者上下文。

可能的局部结果：

- 重大可执行问题；
- 没有新的重大可执行问题；
- 被真正的决策/证据缺口阻塞。

是否已达到一次干净的、覆盖完整的轮次，由父工作流决定，而不是由个别评审者决定。

### 可选的 DELTA

针对性的修复检查可以证明某个修复关闭了其对应问题，且没有破坏其直接影响锥。它是有用的证据，但修复过程中一次可选的内部 DELTA 检查本身不能接受该章节；接受仍然需要一次计数评审。

### INTEGRATION

在已接受的活跃叶子章节于实际功能 head 上组合完成之后，对组装后的功能做跨章节评审。它聚焦于涌现行为，而不是重放每一条章节代码。

## 2. 单次干净评审的章节接受

只有当以下条件全部成立时，章节才被暂时接受：

- 章节契约与 base/head 稳定且已记录；
- 必需的检查通过，或外部证据阻塞项已被明确说明；
- 没有未解决的 `Must Fix`（必须修复）、未接受的 `Should Fix`（应当修复）或阻塞性 `Needs Decision`（需要决策）；
- 延后的工作有明确的后续所有者，且不会使当前中间状态无效；
- 一次全新的、覆盖完整的完整 `SECTION` 评审未发现新的重大可执行根因。修复之后，除非重置触发器生效，一次针对修复增量及其影响锥的干净评审即已足够。

### 连续干净记录

初始化 `clean_streak = 0`。它仍记录在 `FEATURE-STATE.md` 中以备查，但接受不再依赖它达到任何特定值。

- 干净的完整评审 -> `clean_streak += 1`。
- 新的重大可执行问题 -> `clean_streak = 0`。
- 修复 -> 在随后某次完整评审变干净之前，记录保持 `0`。
- 可选的 DELTA 验证 -> 对记录无影响。
- 已关闭根因的重复表述 -> 本身不会重置。
- 无依据假设/风格偏好/非阻塞技术债 -> 本身不会重置。

计数评审者绝不能被预先告知“上一轮是干净的”或先前的诱导性结论。

## 3. 五轮硬上限

对每个活跃章节尝试：

- 计数的完整 `SECTION` 评审最多：**5** 次。
- 软上限：**无**。
- 接受条件：在这五次之内出现一次干净的、覆盖完整的计数评审。
- 同一章节尝试禁止第 6 轮。

示例：

```text
R1 clean
=> accepted in 1 round
```

```text
R1 findings -> repair
R2 clean review of the repair delta plus impact cone
=> accepted in 2 rounds
```

```text
R1 findings -> repair
R2 findings -> repair
R3 findings -> repair
R4 findings -> repair
R5 findings -> repair
=> not accepted; hard-cap split, because no round was clean
```

## 4. 为什么硬上限恢复选择拆分而不是询问是否继续

五次未收敛的完整评审被视为关于分解的证据，而不是增加评审预算的请求。

常见的证据模式：

- 多个相互独立的行为被放进了一个章节；
- 一个章节跨越多个状态/所有权边界；
- 修复反复扰动相邻契约；
- 测试判定基准过宽或过于间接；
- 展开/迁移/收缩各阶段被压缩在一起；
- 使能重构与功能行为纠缠；
- 隐藏的跨章节依赖被留在了章节内部。

因此恢复过程会：

1. 把失败的代码状态保留在 `agent-kit/backup/***` 上；
2. 总结全部五轮评审；
3. 让一个 `[tier: plan]` 子代理只对该章节再分解；
4. 校验新的后代计划；
5. 从失败父章节的原始 `section_base` 重新开始实现。

不要仅仅因为达到了硬上限、或因为需要在递归深度 `1`–`3` 做一次技术性拆分，就询问用户“继续吗？”。自主完成这些拆分并恢复执行。当分解暴露出真正的用户拥有的语义决策，或下一次拆分将产生递归深度 `4+` 时，向人类提问是合适的；后一种情况下应询问是授权更深层递归，还是对受影响边界重新规划。

## 5. 集成检查点

当后续章节开始使用新建立的跨章节契约时使用检查点（integration checkpoint），包括：

- API 生产者 + 第一个真实消费者；
- schema 展开 + 读/写迁移；
- 权限策略 + 执行路径；
- 生产者 + 队列/worker + 重试行为；
- 新的状态所有者 + 下游消费者；
- 功能开关 + 新旧路径对等性；
- 组合之后的独立开发分支。

检查点证据应包括组合 head、所含章节、被测契约、正常/负面/部分失败路径、命令/结果、回滚/停用路径，以及已知的尚未包含的章节。

检查点结果：

- `checkpoint-passed`；
- `checkpoint-blocked`；
- `checkpoint-insufficient-evidence`。

当实际组合推翻了某个章节假设时，检查点可以使先前的局部证据失效。保留原始的评审/重规划谱系，而不是改写历史。

## 6. 最终集成评审

当所有活跃叶子章节被接受之后，对照原始契约评审组装后的功能。

### 原始意图

- 行为是否满足原始的用户/运维结果？
- 非目标是否仍被遵守？
- 每条需求是否都映射到了实现与证据？

### 跨章节契约

- API 请求/响应与错误语义；
- schema/数据所有权与迁移顺序；
- 状态所有权与同步；
- 授权/租户一致性；
- 事件顺序、重试、幂等、取消；
- 共享 UI 状态与加载/错误/空状态；
- 清理与功能开关生命周期。

### 端到端与运维

- 有代表性的正常路径；
- 负面权限/输入路径；
- 部分失败/重试路径；
- 回滚/停用行为；
- 日志/指标/追踪/审计信号；
- 相关场景下的性能/资源边界；
- 安全/隐私/机密处理；
- 文档/配置/运行手册完整性。

### 分支完整性

- 只存在与功能相关的变更；
- 生成工件可复现；
- 测试没有被削弱以强行变绿；
- 临时脚手架已被移除或被明确归属；
- 活跃后代 head 与评审证据对应实际的功能 head。

## 7. 重置与证据失效

当一次重大变更改变了以下内容时，该章节评审尝试应被视为新的基线：

- 章节目标或验收标准；
- 公共 API/序列化契约；
- schema/数据所有权/迁移顺序；
- 认证/授权/租户/隐私语义；
- 并发/顺序/重试/幂等/破坏性行为；
- 架构/状态所有者/依赖方向；
- 发布/回滚/功能开关语义；
- 超出已冻结契约的范围；
- base/head 超出被跟踪的实现/修复操作。

硬上限再分解强于普通重置：父尝试被退役，后代从父章节的原始基点开始。

## 8. 人类决策点

需要用户/负有责任的所有者：

- 含糊的业务/产品行为；
- 兼容性策略选择；
- 迁移/回填含义；
- 可接受的数据/安全/运维风险；
- 尚未指明时的发布人群/时机策略；
- 相互冲突的权威需求。

不需要用户批准的情况：

- 创建硬上限备份分支；
- 调用 `[tier: plan]` 分解者；
- 拆分技术性章节；
- 创建重试分支/worktree；
- 提取第一个后代并恢复实现。

以上全部在递归拆分深度 `3` 以内保持自主。只有在创建深度 `4+` 后代之前才需要人类批准，除非另一个真正的用户拥有的决策已经要求暂停。

## 9. 最终就绪门禁

只有在以下条件全部成立时才判定 `mergeable`（可合并）：

- 所有活跃叶子章节均被暂时接受；
- 因硬上限拆分而退役的父章节拥有完整的谱系/证据；
- 所有完整功能需求均已覆盖；
- 必需的集成检查点通过；
- 最终集成评审没有未解决的重大合并阻塞项；
- 完整功能确定性检查通过，或明确的外部阻塞项/残余风险已被报告；
- 发布、回滚、迁移、可观测性与清理义务已解决或被明确接受。

否则使用 `not-mergeable`（不可合并）或 `insufficient-evidence`（证据不足）。
